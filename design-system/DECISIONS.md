# Design System Decisions

New decisions go on top. Each one says what was decided, why, and what it changes.

| # | Date | Decision | Why | Impact |
|---|---|---|---|---|
| DS-37 | 2026-10-20 | Three library files, one-way dependencies: *DKB Foundations* (tokens, styles) ← *DKB Components* (Core: shadcn-based, platform-agnostic, icons) ← *DKB Commerce* (shared composite parts: page shell, product, checkout, status; and the layout templates) ← feature files. Platform differences, lightest tool first: brand look → `brand` mode; content → properties, exposed nested instances or a slot; a stable layout difference → variant `platform=b2r|b2e|portal`; mostly different → a prefixed component in Commerce (`b2e/…`, `b2r/…`). No per-platform library until one platform owns many parts | Core stays close to shadcn and changes rarely; Commerce changes with the products and is published on its own; templates must contain real shell parts, which Core can't depend on | Templates moved from DKB Components to DKB Commerce; `components.json` has a `file` per component and `sync_check.py` one fingerprint per library file |
| DS-36 | 2026-10-20 | Page layout standard (`patterns/layouts.md`): one 12/8/4-column grid with content width 1312 on every page; grey page (`bg.subtle`) with white cards for B2R and B2E; 5 shells (storefront, focused, account, workspace, auth) and 10 templates; desktop header rows chosen per platform; sticky bottom action bar on mobile checkout and forms | The live B2R site uses 4 content widths, 4 backgrounds and 4 card radii; shadcn covers app shells but not shop pages | Replaces the B2E "white surface" decision (2026-10-19). Shell parts become Commerce components |
| DS-35 | 2026-10-20 | Date picker: Jalali calendar in a popover on desktop, in a drawer on mobile | Follows DS-32; a calendar is easier than three selects for delivery and report dates | Birth dates may still use three selects (spec note) |
| DS-34 | 2026-10-20 | Chart palette `chart.1–5`: brand 600 (B2R navy #245CAC / B2E violet #7C3AED), teal #0D9488, orange #EA580C, pink #DB2777, lime #65A30D, always in this order | Passes the colour-blind and contrast checks on white (shadcn's default palette fails them); status colours stay reserved for status | 4 new single-step primitives (teal, orange, pink, lime 600) and 5 semantic tokens; shadcn `--chart-1…5` and `--sidebar-*` now mapped |
| DS-33 | 2026-10-20 | Overlays take custom content through an instance-swap `content` property that defaults to a `slot` placeholder; every menu is built from one shared `menu-item` row | Figma instances can't take new children, and detaching breaks the library link; one row type keeps dropdown, context menu, menubar, command and combobox identical | Designers and agents build content as local `content/…` components; the audit fails a visible slot |
| DS-32 | 2026-10-20 | On mobile, `dialog` becomes a bottom sheet (`drawer`); `alert-dialog` stays centred on both | Matches today's B2E/B2R pattern; bottom sheets are easier to reach with one hand | Dialog specs describe both; mobile designs use `drawer` |
| DS-31 | 2026-10-20 | Overlay width tokens matching shadcn exactly: `width.hover-card` 256, `width.popover` 288, `width.sheet` 384, `width.dialog` 512 (new size steps 256/288/384/512) | Overlays had no width tokens; shadcn parity | 4 + 4 new Figma variables |
| DS-30 | 2026-10-20 | `shadow.dialog` = `shadow.lg` (was xl), as shadcn dialog, sheet and toast | shadcn parity | Effect style updated; sheet, drawer and toast reuse it. Effect styles are now fingerprinted with their values |
| DS-29 | 2026-10-20 | z-index: `dropdown` renamed `popover` and moved above `dialog` (sticky 1100 · overlay 1300 · dialog 1400 · popover 1500 · toast 1600 · tooltip 1700) | A menu or select opened inside a dialog rendered behind it | Code-only token |
| DS-28 | 2026-10-20 | Every disabled control (button, icon-button, input, textarea, select, native-select, field, toggle, slider, OTP…) shows its normal look at `opacity.disabled` (shadcn `disabled:opacity-50`) | One rule, same as shadcn; the token-based grey look of buttons and inputs didn't match checkbox/radio/switch (DS-23) | `bg.disabled` / `text.disabled` stay in the tokens for non-control use (e.g. unavailable product text) but no component uses them now |
| DS-27 | 2026-10-20 | Calendar and date picker are Jalali only: Persian digits, week starts Saturday | Every DKB product uses Jalali dates | No Gregorian variant for now |
| DS-26 | 2026-10-20 | Form fields as atoms plus a composite: `input`, `textarea`, `label` match shadcn; `field` (label + control + helper/error) is what forms use. `input-field` becomes `field` | 1:1 with shadcn and code, while agents still get one composite for forms | `input-field` is replaced in batch 1; `components.json` changes |
| DS-25 | 2026-10-20 | The 8 shadcn AI / conversation components (attachment, bubble, code block, marker, message, message scroller, questionnaire, trace) are deferred | DKB has no chat or assistant feature planned yet | Listed as deferred in COVERAGE.md |
| DS-24 | 2026-10-20 | Every shadcn/ui component gets a DKB equivalent before complex product components (header, product card, price…) | Base parity first; product components are built from it | Plan and status in `COVERAGE.md`; "implement" = Figma component + spec + `components.json`; production code stays with the dev team |
| DS-23 | 2026-10-20 | Disabled checkbox, radio and switch keep their normal look (checked or not) at 50% opacity, via new token `opacity.disabled` (shadcn `disabled:opacity-50`) | Greying them out with `bg.disabled` made on and off look the same (reported on the switch) | Applies to the whole control including its label. Extended to every control by DS-28 |
| DS-22 | 2026-10-20 | Focus ring matches shadcn/ui exactly: `border.focus` = neutral-400 (shadcn `--ring`), ring = 3 px spread shadow of `ring.default` (neutral-400 at 50%); fields in error get `ring.destructive` (red-600 at 20%) | Design lead decision: same look as shadcn and `@digikala/ui-kit` (`ring-[3px] ring-ring/50`) | Replaces the brand-coloured `border.focus` (brand-600). New tokens `ring.default`, `ring.destructive`, effect styles `shadow.focus-ring`, `shadow.focus-ring-destructive`. Trade-off: the ring is subtle (focus border 2.52:1, below WCAG 2.2 focus-appearance guidance); it is listed as info in the contrast report |
| DS-21 | 2026-10-20 | New token `border.control` (neutral-500, 4.74:1) for the boundary of checkbox, radio and switch | These controls show their state only through their shape, so WCAG 1.4.11 (3:1) applies; `border.input` is 1.48:1 | Used by checkbox, radio, switch; text inputs keep `border.input` (DS-20) |
| DS-20 | 2026-10-19 | Input border stays light: `border.input` = neutral-300 (1.48:1 on white) | Design lead decision; keeps the shadcn look | Fields must not rely on the border alone: always a visible label, and `bg.muted` fill or focus ring where extra cue is needed |
| DS-19 | 2026-10-19 | Two deliberate deviations from DTCG: line heights in px (not a multiplier), and our own `manifest.json` for modes instead of the DTCG resolver format | Px matches Figma exactly; resolver tooling is still immature | Revisit when Figma and Style Dictionary support the resolver format |
| DS-18 | 2026-10-19 | Motion and z-index tokens are code-only | Figma variables can't drive transitions or stacking | Marked `skip` for the Figma sync |
| DS-17 | 2026-10-19 | Figma scopes and visibility are stored in the token JSON (`$extensions.dkb.figma`) | Set once, applied by the sync; no hand-set Figma settings to drift | Background tokens appear only for fills, text tokens for text and icons, border tokens for strokes |
| DS-16 | 2026-10-19 | Components may use the space, radius, size and border-width scales directly; colour primitives and the brand ramp are hidden | No semantic spacing layer, so the old "semantic only" rule couldn't be followed | Rule in README principle 2 |
| DS-15 | 2026-10-19 | Build writes `shadcn-compat.css` and `tailwind-theme.css` | Developers and `@digikala/ui-kit` keep shadcn names while design uses property-based names | No renames needed in code to adopt the tokens |
| DS-14 | 2026-10-19 | Semantic colours grouped by property: `bg.*`, `text.*`, `border.*` (replaces shadcn names) | Says where each token goes; enables Figma scoping; removes three identical vague tokens (muted, accent, secondary) | Supersedes the "shadcn names" naming rule from v0.1 |
| DS-13 | 2026-10-19 | Brand layer is an 11-step ramp with the main colour always at step 800 (replaces 10 role tokens) | Role tokens couldn't support dark mode; a fixed step lets one semantic mapping serve every brand | Navy ramp regenerated with `#093672` at 800 (supersedes DS-7). New tenant = one hex |
| DS-12 | 2026-10-19 | Domain statuses map to tones in component specs, not to tokens | Keeps the token set small; one place to change a status colour | Status badge gets a `tone` prop; the status dictionary lives in its spec |
| DS-11 | 2026-10-19 | Screen switch at 1024 px: Mobile values below, Desktop from 1024 | Tablets (768–1023) are touch devices and use single-column layouts (B2E responsive rules) | Control heights 36/40/48 on mobile and tablet, 32/36/40 on desktop |
| DS-10 | 2026-10-19 | Control radius 8 px (`radius.md`); one radius scale (2, 4, 8, 12, 16, 24, full) | Replaces the old double set (shadcn + legacy 4/8/12/16) and the 6 px live value | Buttons, inputs, selects use `radius.control` |
| DS-9 | 2026-10-19 | Neutral greys are Tailwind `neutral` | Matches the ui-kit default; least migration | Secondary text is neutral-600 (7.8:1 on white), not neutral-500 |
| DS-8 | 2026-10-19 | B2E primary is `#5B21B6` (violet-800) for now | Matches code; Figma's v4 violet-800 is a slightly different shade. To be reviewed later | B2E `brand.800` = `color.violet.800` |
| DS-7 | 2026-10-19 | ~~B2R navy ramp generated around `#093672`, which sits at step 900~~ (superseded by DS-13) | `#093672` is a dark colour; placing it at 900 gives usable light tints (50–300) for backgrounds | B2R primary = `color.navy.900` |
| DS-6 | 2026-10-19 | Light mode only for now; tokens are dark-ready | Shared decision "no dark mode for now" | `semantic` has one mode (Light); a Dark mode can be added without renaming tokens |
| DS-5 | 2026-10-19 | Status colours use five tokens each (solid, on-solid, subtle, subtle text, border) | Old Theme collection mixed meanings of "foreground" (Gap #17); status colours were hard-coded (Gaps #12, #13) | Badges, alerts and order/payment/cheque statuses all map to these tokens |
| DS-4 | 2026-10-19 | Repo JSON is the source of truth for token values | Reviewable history; one pipeline instead of three sources (Gap #2) | Figma variables are written from the JSON; edits in Figma count as drift |
| DS-3 | 2026-10-19 | Brand modes start with B2R and B2E | The two main platforms; portal tenant identities are still pending | Portal tenants use B2R or B2E until they get their own mode |
| DS-2 | 2026-10-19 | Build fresh Figma libraries: *DKB Foundations* and *DKB Components* | The current DS - Shadcn and DS - Components files are inefficient and drifted | Old files stay as reference until migration |
| DS-1 | 2026-10-19 | Primary font: Digikala font (replaces IRANYekanX) | Design lead decision | Type tokens and text styles use the Digikala font family |
